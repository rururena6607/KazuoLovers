# バレー部 サーブ・レシーブ・アタック分析アプリ 実装計画書

開発メンバー（ガブ、ひろし、とりはる）

## 0. この文書の目的

3人がそれぞれ AI を使いながら並行して実装する。このとき起きやすいのは次の3つである。

- 同じファイルを複数人（と各自の AI）が同時に書き換え、マージで衝突する
- AI が頼まれていない箇所まで直し、他人の担当部分を壊す
- 画面・データ・計算の間の約束（記録の形や関数の引数）が人によって食い違う

本書は、**誰がどのファイルを持つか**、**約束をどう固めるか**、**AI に何をさせ、何をさせないか**を先に決めて、これらを防ぐ。何を作るかは [要件定義書](requirements.md) に従う。回ごとの担当の早見表は [担当表](weekly-assignments.md) にある。

## 1. 基本方針

1. **1つの範囲には1人の所有者**がいる。所有者以外はその範囲のファイルを直接書き換えない。
2. **約束は `src/contracts/` に集める**。第1段階で固め、以後の変更は専用の PR で行う。
3. **1タスク＝1ブランチ＝1PR**。PR は小さく、短期間でマージする。
4. **AI には担当範囲の中だけを編集させる**。それ以外の変更が必要なときは、AI に書かせず提案として出させ、人が判断する。
5. **指標の計算はテストが合否の基準**。JVA の公式記録票の数字をテストに使い、CI が通らない PR はマージしない。

## 2. 役割と担当者

| 役割 | 担当者 | 主な責任 |
| --- | --- | --- |
| 画面・記録 | ガブ | 画面の骨組みとデザイン（1c スコアボード案）、記録画面（サーブ・レシーブ・アタック・練習）、PWA、ビルド設定、CI、Vercel |
| データ・サーバ | ひろし | Supabase（テーブル、RLS、Auth、Realtime）、記録の保存と読み込み、送信待ちと再送、Edge Functions（Gemini・LINE）、ログインと管理画面 |
| 計算・分析 | とりはる | 指標の計算（JVA の式）、得点とサーブ権の更新、座標からゾーンへの変換、集計、分析画面、ヒートマップ、グラフ、セット別の結果、CSV |

得意なことに合わせて入れ替えてよい。入れ替えたときは、3 節の所有範囲もあわせて直す。

### 2.1 PR のレビュアー

**PR のレビュアーは、実装者以外の1人**とする。順番を固定して、だれか1人に偏らないようにする。

| 実装者 | レビュアー | 主に見ること |
| --- | --- | --- |
| ガブ | とりはる | 記録画面が約束どおりの記録を作っているか、得点の更新を正しく呼んでいるか |
| ひろし | ガブ | 画面から使いやすい形でデータを返しているか、未送信の表示が画面と合っているか |
| とりはる | ひろし | 指標の式が要件定義書 5 章と同じか、テストに JVA の記録票の数字を使っているか |

- `src/contracts/` を変える PR は、**3人全員**の承認を要る。
- 要件定義書・本書を変える PR も、3人全員の承認を要る。

### 3.1 依存の向き

```
features ──▶ lib/stats, lib/rally, lib/court ──▶ contracts
   │  ──────▶ lib/data ─────────────────────────▶ contracts
   └───────▶ components, app
supabase/functions ──▶ lib/stats ──▶ contracts
```

- `lib/stats`・`lib/rally`・`lib/court` は **`contracts` にだけ依存し、React にも Supabase にも依存しない**純粋な TypeScript にする。テストを速く回せ、Edge Functions（LINE の返信文の集計）からも同じ関数を使える。
- `lib/data` は `contracts` のインターフェース（`RecordRepository`）を実装する。画面は `RecordRepository` だけを使い、Supabase を直接呼ばない。
- 画面を作る人は、データがまだなくても**偽物（フェイク）の `RecordRepository`** を使って並行して進める（T-01 で用意する）。

### 3.2 言語と主な技術

| 項目 | 決定 |
| --- | --- |
| 言語 | **TypeScript**（`strict: true`） |
| 画面 | React ＋ Vite。コート図は SVG、ヒートマップは Canvas、グラフは Chart.js |
| データ | `@supabase/supabase-js`。送信待ちは IndexedDB |
| PWA | `vite-plugin-pwa` |
| テスト | Vitest。`lib/` の純粋な関数は必ずテストを書く |
| Edge Functions | Deno（Supabase の標準）。`lib/stats` は外部の依存を持たないので、そのまま読み込める |
| 公開 | Vercel。`main` に入ると自動で公開される |

## 4. 約束（`src/contracts/`）

第1段階のタスク T-01 で、次の型とインターフェースを**コードとして**作り、全員の承認を得てマージする。名前と引数は T-01 のレビューで確定する。以下は叩き台である。**T-01 のマージ後は `src/contracts/` のコードが正**で、下の叩き台とは名前が違うところがある（記録に `kind` を足した、`pendingCount` を `subscribePending` にした、など）。

```ts
// ---- 記録（要件定義書 7 章のテーブルと同じ形） ----
export type ServeType = 'float' | 'jump_float' | 'jump' | 'other';
export type Grade = 'A' | 'B' | 'C' | 'D';

export interface ServeRecord {          // 自チームのサーブ1本
  clientId: string; setId: string; serverId: string; serveType: ServeType;
  fromX: number | null; toX: number | null; toY: number | null;   // 0.0〜1.0
  result: 'ace' | 'in' | 'miss'; missType: 'net' | 'out' | 'other' | null;
  reception: Grade | null; receiverId: string | null;            // 相手選手
  targetZone: number | null;                                      // 練習モードのみ
  recordedAt: string;
}
export interface ReceptionRecord {      // 相手のサーブ1本と自チームのレシーブ
  clientId: string; setId: string; receiverId: string | null;    // 相手ミスなら null
  oppServerId: string | null; oppServeType: ServeType | null;
  atX: number | null; atY: number | null;
  result: 'ace' | Grade | 'opp_miss';
  recordedAt: string;
}
export interface AttackRecord {         // 自チームのアタック1本
  clientId: string; setId: string; attackerId: string;
  attackType: 'left' | 'center' | 'right' | 'back' | 'other' | null; isBack: boolean;
  toX: number | null; toY: number | null;
  result: 'kill' | 'continue' | 'error' | 'blocked';
  prevReception: Grade | null;
  recordedAt: string;
}
export interface PointRecord {          // 1点ずつの得点
  clientId: string; setId: string; side: 'us' | 'opp';
  cause: 'ace' | 'serve_miss' | 'opp_miss' | 'aced' | 'kill' | 'attack_error' | 'blocked' | 'manual';
  sourceId: string | null; ourScore: number; oppScore: number;
  recordedAt: string;
}

// ---- lib/rally が提供 ----
export interface RallyState { ourScore: number; oppScore: number; serving: 'us' | 'opp'; }
/** 記録1本から、入る得点（なければ null）を決める */
export type PointFor = (rec: ServeRecord | ReceptionRecord | AttackRecord) => 'us' | 'opp' | null;
/** 得点を1つ足したあとの状態を返す。サーブ権も移す */
export type ApplyPoint = (state: RallyState, side: 'us' | 'opp') => RallyState;

// ---- lib/stats が提供（値はすべて%。打数0なら null） ----
export interface ServeStats { attempts: number; aces: number; effects: number; misses: number;
  efficiency: number | null; aceRate: number | null; missRate: number | null; }
export interface ReceptionStats { receptions: number; excellent: number; good: number; aced: number;
  successRate: number | null; acedRate: number | null; }
export interface AttackStats { attempts: number; kills: number; errors: number;
  killRate: number | null; efficiency: number | null; }

// ---- lib/data が提供 ----
export interface RecordRepository {
  save(rec: ServeRecord | ReceptionRecord | AttackRecord | PointRecord): Promise<void>; // 失敗しても送信待ちに残す
  remove(clientId: string): Promise<void>;
  listBySet(setId: string): Promise<SetRecords>;
  subscribe(matchId: string, onChange: (recs: SetRecords[]) => void): () => void;   // 戻り値で購読を解除
  pendingCount(onChange: (n: number) => void): () => void;                         // 未送信件数
  retry(): Promise<void>;
}
export interface SetRecords { setId: string; serves: ServeRecord[]; receptions: ReceptionRecord[];
  attacks: AttackRecord[]; points: PointRecord[]; }
```

- **定数**（参考値にする本数「10本」、セットの点数の初期値「25点」、ゾーンの分け方）も `contracts` の `config.ts` に置く。値を変えるのは、その値を使う範囲の所有者の PR だけとする。
- `contracts` を変えるときは、**約束の変更だけを含む PR** を先に出し、3人全員の承認を得てからマージする。自分の機能の PR に `contracts` の変更を混ぜない。

## 5. ブランチと PR の運用

### 5.1 ブランチ

- `main` は常にビルドとテストが通る状態に保つ。**`main` への直接の push は禁止**（ブランチ保護で強制する）。
- 作業ブランチは `main` から作り、名前は `<役割>/<タスクID>-<短い説明>` とする。
  - 例：`ui/T-11-serve-record`、`data/T-15-offline-queue`、`stats/T-06-jva-metrics`
- ブランチの寿命は **2日以内**を目安にする。長くなりそうなタスクは分ける。
- 作業を始める前と PR を出す前に、`main` の最新を取り込む（`git pull --rebase origin main`）。

### 5.2 PR

- **1タスク＝1PR**。変更は 300 行程度までを目安にする。
- タイトルは `[T-xx] 内容`。本文に、対応する要件 ID（F-xx）を書く。
- マージの条件は次の3つ。
  1. CI（型チェック、Lint、テスト、ビルド）が通る
  2. レビュアー（2.1）の承認が1つある
  3. PR テンプレートのチェックリストがすべて埋まっている
- マージ方法は squash とし、履歴を1タスク1コミットにする。

PR テンプレートのチェックリスト（T-00 で `.github/pull_request_template.md` に置く）：

```
- [ ] 変更したのは自分が所有する範囲だけ（または所有者の承認がある）
- [ ] contracts の約束を変えていない（変える場合は別の PR にした）
- [ ] lib/ を変えた場合はテストを追加・更新し、ローカルで通した
- [ ] AI が書いた部分を自分で読み、説明できる
- [ ] 秘密情報（Supabase の service_role キー、Gemini・LINE のキー）を含めていない
- [ ] 選手の名前を外部 AI に送る処理を入れていない
- [ ] 無関係な整形・名前の変更・依存の更新をしていない
```

### 5.3 衝突を起こしやすいファイルの扱い

| ファイル | ルール |
| --- | --- |
| `package.json`、`package-lock.json` | 依存の追加はガブに依頼する。自分で追加する場合は、その行だけを追加する小さな PR にする |
| `vite.config.ts`、`tsconfig.json` | ガブだけが変更する |
| 画面遷移とタブバー（`src/app/`） | ガブが所有する。画面を追加する人は、登録する1行を依頼する |
| 色・文字の変数（`src/app/theme.css`） | ガブが所有する。新しい色が必要なときは依頼する |
| `supabase/migrations/` | ひろしだけが追加する。テーブルを変えるときは、先に `contracts` の約束を変える |
| 環境変数（`.env.local`） | コミットしない。必要な変数名は `.env.example` に書く（ひろし） |
| テスト用のデータ | 各範囲の `__tests__/` に置く。共有しない |

### 5.4 進捗の管理

- タスク（7 節の T-xx）は GitHub の Issue にして、担当者を割り当てる。GitHub Projects のボードで「未着手／作業中／レビュー中／完了」を管理する。
- **これから触るファイルが他人の担当に入る場合は、作業前に Issue でその所有者に知らせる。**

## 6. AI の使い方

各自が使う AI（Claude Code、ChatGPT、Copilot など）が何であっても、同じルールで使う。

### 6.1 作業を始めるときに AI へ渡すもの

1. [要件定義書](requirements.md) と本書
2. 担当するタスクの Issue（T-xx の内容、要件 ID）
3. `src/contracts/` の約束
4. 自分の担当範囲の既存のコード

### 6.2 AI への指示のひな形

```
あなたはバレー部のサーブ・レシーブ・アタック分析アプリの <役割> 担当の開発を手伝う。
docs/requirements.md と docs/implementation-plan.md に従うこと。

タスク: T-xx <内容>
対応する要件: F-xx

守ること:
- 編集してよいのは <担当範囲> の中だけ。それ以外のファイルは変更しない。
- src/contracts/ の型やインターフェースを変える必要がある場合は、変更せずに理由と案を示す。
- 指標の式は要件定義書 5 章（JVA の公式記録票の式）に従い、独自に変えない。
- 参考値の本数などの定数は contracts/config.ts を使い、数値を直接書かない。
- TypeScript で書き、any を使わない。
- lib/ の関数には Vitest のテストを書く。
- 依存ライブラリの追加・更新、無関係な整形や名前の変更はしない。
- API キーをブラウザのコードに書かない。Gemini と LINE は Edge Functions からだけ呼ぶ。
```

### 6.3 AI にさせないこと

- 担当外の範囲、`contracts`、ビルド設定、`supabase/migrations/` の書き換え（所有者以外の場合）
- ファイル全体の自動整形、一括リネーム、依存の一括更新（差分が膨らみ、他人の作業と衝突する）
- 指標の式を「わかりやすく」変えること（JVA の式から外れる）
- RLS を外したり緩めたりして、エラーを消すこと
- 選手の名前を Gemini に送ること
- 秘密情報をコードやコミットに入れること
- テストを通すために、テストや合格条件を弱めること

### 6.4 人の責任

- AI が書いたコードは、PR を出す前に**全行を自分で読む**。説明できないコードはマージしない。
- テストは自分の手元で実行してから PR を出す（`npm test`）。
- AI が「`contracts` を変えるべき」と提案した場合は、人が判断し、4 節の手順で約束の変更 PR を出す。
- リポジトリ直下に `CLAUDE.md`（および他の AI 用に `AGENTS.md`）を置き、6.2・6.3 の内容を書いておく（T-00）。AI が作業のたびに自動で読むようになる。

## 8. 指標のテスト

`lib/stats` のテストには、JVA の公式記録票（要件定義書 5 章「指標」の出典）の数字を使う。記録票と同じ値が出ることを合否の基準にする。

| テスト | 入力 | 期待する値 |
| --- | --- | --- |
| サーブ効果率（チーム） | 打数61、エース2、効果25、ミス4 | 11.9% |
| サーブ効果率（マイナス） | 打数7、エース0、効果0、ミス2 | −7.1% |
| サーブレシーブ成功率 | 受数64、A23、B11 | 44.5% |
| アタック決定率 | 打数110、得点35 | 31.8% |
| 打数0 | 打数0 | null（画面では「−」） |

表示は小数第1位に丸める。丸めは画面に出すときだけ行い、集計の途中では丸めない。

## 10. 決まりごと

- 毎回の授業の初めに、その週のタスクと担当を確認する。授業のない週（第2回）は、週の初めにオンラインで確認する。触るファイルが重なりそうなタスクは、この時点で順番を決める。
- 期限に間に合わないタスクは、すぐに2人に知らせて、捨てるか後ろへ回すかを決める。
- 要件の変更は、要件定義書を直す PR を先に出す。口頭で決めたことも、要件定義書か Issue に書いてから実装する。
- 部員に試してもらった意見は Issue にして、要件定義書を直すかどうかを3人で決める。
- 困ったら、所有者に聞いてから相手の範囲を触る。AI に聞いて済ませない。

### 10.1 API のアカウント

**API のアカウントは、学校のメールアドレスで作る。** 個人のメールアドレスや、個人の Google・LINE のアカウントでは作らない。

| サービス | 作る人 | 作るもの | ほかの2人の入り方 |
| --- | --- | --- | --- |
| Supabase | ひろし | 組織（Organization）とプロジェクト | 学校のアドレスで各自のアカウントを作り、組織のメンバーに招待してもらう |
| Gemini API（Google AI Studio） | ひろし | API キー | 招待しない。キーは Supabase の Edge Functions の環境変数にだけ置く |
| LINE Developers | ひろし | プロバイダーと Messaging API のチャネル、LINE 公式アカウント | 学校のアドレスで各自のアカウントを作り、チャネルの権限を付けてもらう |

- API キーやチャネルのシークレットは、チャットやコミットに貼らない。必要な人には Supabase の環境変数の画面で見てもらう
- アカウントを作ったら、使ったアドレスとサービス名を Issue に書いておく（パスワードは書かない）
- 学校のアドレスで作れないサービスがあった場合は、個人のアドレスで作らずに3人で相談し、先生に確認する
